## 铁律：改完必过独立审查

> **任何一次实质性修改之后，必须派一个「没参与编写」的 Claude 独立审查一遍。**

为什么这条是铁律 —— 有真实教训：

本技能在迭代了十几轮之后，作者自认为已经很完善了。派了一个全新的 agent 空着脑子读一遍，**一次就报出 16 个问题**，其中包括：

- 模板骨架写着 `name: <课程名>-teacher` —— 但 `name` 不能是中文、`description` 不能有尖括号，**照抄骨架会被自己的校验器判错**
- 模板里有一整段**复制粘贴残留的重复小节**
- 校验器收尾还打印着上游的「四要素：输入输出」执行型话术
- 文档说乱码判据是「中文占比 < 1% 且可疑字符 > 20%」，脚本其实只算「可疑 > 10%」

**全都是作者自己看不见的。** 改了十几轮之后，人对自己的措辞会脱敏 —— 你知道自己想说什么，就读不出自己写了什么。

**所以：作者的自信不算数，陌生人的一遍阅读才算数。**

## 独立审查怎么跑

用 Agent 工具派一个 `general-purpose`，**不要给它你的想法和上下文**（空着脑子才能看见你看不见的）。

提示词模板：

```
请对一个 Claude Code Skill 做独立的一致性审查。你没有参与它的编写，
请以陌生人的视角严格挑毛病。

审查对象：
<skill 目录>

它的用途：<一句话>

它已经产出的一个真实产物（用于交叉验证规范是否可执行）：
<产物目录>

请重点检查：
1. 自相矛盾 —— 同一机制在不同文件里说法不一致（如某处说"要做 X"，示例却违反 X）
2. 主流程缺口 —— SKILL.md 的步骤漏掉了 references 里定义的关键机制
3. 定位错位 —— 为「执行型 skill」写的规则被用在「教学型 skill」场景
4. 脚本与文档不符 —— 脚本实际行为 vs 文档描述
5. 流程不完整 —— 从"用户给资料"到"能上课的老师"这条链路有没有断掉的环节
6. 失效的示例 —— 文档里的 ✅/❌ 例子是否还和当前规则一致

输出要求：
- 按严重程度排序（严重 / 中等 / 轻微）
- 每条：问题 → 证据（文件:行号 + 原文）→ 为什么是问题 → 建议怎么改
- 不要复述文件内容，不要夸奖，只报问题
- 如果某类问题没找到，明确说"未发现"
- 不要修改任何文件，只报告
```

**跑完之后**：区分「母体规则的锅」和「单个产物的锅」，分别修（见 SKILL.md Step 6）。

## 回归测试

每次改完 scripts/ 或校验规则，跑这三个样本：

```bash
S=<本技能目录>
V=$S/scripts/validate_output.py

# ① 正向：本技能自身（不该有误报）
python "$V" "$S"

# ② 正向：一个合格的产物（不该有误报）
python "$V" "<一个产出的老师目录>"

# ③ 负向：故意漏掉新规范的样本（必须报出对应警告）
```

**负向样本尤其重要** —— 只测正向，你永远不知道校验器是不是已经失效了。

构造负向样本：做一个「有老师外壳、但缺机制」的 skill（没有选择题标记、没有示范模式、没有作业分类），确认三条警告都报出来。

## 改哪一层？

| 症状 | 改哪 | 判据 |
|------|------|------|
| **每个产物都会犯** | 母体（本技能） | 规则没写清 / 工具没做对 |
| 只有某一个产物犯 | 产物自己 | 那份资料的提炼不到位 |
| 校验器报出的、你觉得不该报的 | 校验规则 | 误报会让人忽略真报警 |

**误报是毒药。** 一条总在误报的规则，会让使用者学会无视所有警告 —— 那校验器就全废了。发现误报立刻修，宁可放宽也不要留噪声。

## 发布前检查清单

改完准备发布时：

- [ ] 独立审查已跑过，报出的问题都已处理或明确不处理
- [ ] 回归测试三类样本都跑过（正向 ×2 + 负向）
- [ ] 本技能自身 `validate_output.py` 通过、无警告
- [ ] 如果改了规范，**检查已产出的其他老师 skill 有没有同样的问题**
- [ ] `NOTICE` 里的改动清单已更新（Apache 2.0 第 4(b) 条要求）
- [ ] `README.md` 里的描述与当前行为一致（尤其是机制表）
- [ ] 版本号 / 变更记录已更新（如果用）
